# 13 Final Architecture Review

这一章不再增加新功能，
只做一次真正的 `v1` 总复盘。

到这里为止，
我们要回答的已经不是：

- 下一段代码怎么写

而是：

- `v1` 到底做成了什么
- 它现在的边界到底在哪
- 哪些事情应该留给 `v2`

## 先给 `v1` 下一个准确定义

`mini-cloud v1`
不是：

- 一个完整云厂商
- 一个真正多云的平台
- 一个完整的容器编排系统

它更准确的定位是：

- 一个面向容器应用托管的最小平台控制面

并且这一版的基础设施范围明确收敛到：

- 单 provider
  - 阿里云
- 单类底层节点
  - `ECS`

所以你现在看到的 `v1`，
可以把它理解成：

- “先跑通一条从控制面到节点执行的完整主链”

而不是：

- “一开始就把云平台所有问题一起做完”

## `v1` 到底做成了什么

按主链看，
`v1` 已经把下面这些核心能力串起来了：

1. 控制面
   - 有自己的 API、资源模型和状态存储
2. 节点纳管
   - agent 可以注册节点、上报心跳、汇报容量与状态
3. 调度
   - control-plane 可以按地域和容量做最小放置
4. 发布
   - 用户可以围绕 app / release / deployment 推进一次发布
5. 执行
   - agent 可以在节点上拉镜像、起容器、做基础健康检查
6. 入口
   - 应用可以绑定域名并通过基础入口层对外暴露
7. 运维
   - 已有基础日志、指标、失败重试、节点维护、用量和配额能力
8. 验证
   - 已有项目级检查、集成测试和 smoke 测试

也就是说，
`v1` 已经不是一个“只会存几张表”的半成品，
而是一个：

- 可以在本地开发环境里跑通完整主链
- 也能映射到真实阿里云节点场景

的最小平台雏形。

所以 `v1` 的价值，
主要不是“已经统一了所有云”，
而是“已经把平台骨架做出来了”。

## 从一次发布看整条主链

如果只看一次最典型的应用发布，
`v1` 的执行链路可以压缩成下面这样：

```text
用户提交 release
    │
    ▼
control-plane 创建 deployment
    │
    ▼
调度器选择 region 内合适节点
    │
    ▼
deployment 进入 assigned / deploying
    │
    ▼
node agent 拉镜像并启动容器
    │
    ▼
agent 回传容器状态与健康检查结果
    │
    ▼
deployment 进入 running / failed
    │
    ▼
用户在 UI / API 上看到最终状态、日志和基础指标
```

所以到了这里，
你应该已经能把 `mini-cloud v1`
理解成一个很清晰的系统：

- control-plane 决定“应该发生什么”
- agent 负责让节点上“真的发生”
- 数据库存“这件事现在推进到了哪里”

## `v1` 的边界要说死

这一节很重要，
因为很多系统在第一版做完后最容易出现的问题就是：

- 明明范围已经够大了
- 但还继续偷偷往里面塞第二版需求

`mini-cloud v1`
现在要明确停在这些边界上。

### 1. 只支持阿里云 `ECS` 节点

虽然资源模型里保留了：

- `provider`
- `region`

但实现上还没有真正做：

- AWS / 腾讯云 / Vultr / 裸机

的统一接入层。

### 2. 只支持最小应用托管

`v1` 关注的是：

- 容器应用怎么被部署起来

而不是：

- 给用户卖虚拟机
- 给用户卖数据库
- 给用户卖对象存储

### 3. 运行时仍然是最小实现

`v1` 现在是：

- control-plane + agent + 容器运行时

并没有引入：

- `k3s`
- Kubernetes
- 更正式的 workload 编排层

### 4. 认证、权限、入口都还是基础版

现在的重点是把平台主链做通，
不是把这些外围系统一次做到很重：

- 完整认证与授权
- 完整审计
- 完整多租户隔离
- 正式网关体系

### 5. 真实云资源自动化还不是 `v1` 核心

`v1` 可以映射到真实阿里云节点，
但它现在更偏向：

- 在已准备好的节点池之上做平台控制面

而不是：

- 从零自动创建 VPC / 交换机 / 安全组 / ECS / SLB

这条线以后当然可以做，
但不应该在 `v1` 收尾时继续扩张。

## `v1` 已完成 / `v2` 待做

| 主题 | `v1` 已完成 | `v2` 待做 |
| --- | --- | --- |
| 基础定位 | 最小容器应用托管平台 | 更正式的平台产品边界 |
| 云后端 | 阿里云 `ECS` 节点池 | 多 provider 抽象 |
| 控制面 | API、资源模型、状态推进 | 更强的权限、审计、后台任务体系 |
| 调度 | 按地域和容量做最小放置 | 成本、亲和性、故障域、更多策略 |
| 发布 | `release -> deployment` 主链跑通 | 更完整的回滚、灰度、批次控制 |
| 节点执行 | agent 拉镜像、起容器、回传状态 | 更正式的 runtime / orchestration 底座 |
| 入口 | 基础域名绑定与入口转发 | 更正式的 gateway / ingress 体系 |
| 运维 | 基础日志、指标、重试、维护模式 | 更强的观测、告警、自动化运维 |
| 用量与配额 | 基础 usage / quota / cost preview | 更真实的计费、账单与资源约束 |
| 测试 | check / integration / smoke 主链 | 更完整的真实环境验证和发布流程 |

把这张表看懂以后，
你就会发现：

- `v2`
  - 不是“把 `v1` 推倒重来”

而是：

- 在 `v1` 已经稳定的控制面骨架上继续扩展

## 为什么现在不应该直接把 `v2` 做成大而全

因为如果现在直接跳去做这些事情：

- 多 provider
- 多副本 control-plane
- 更重的认证系统
- 更正式的网关层
- 更复杂的运行时底座

很容易发生两个问题：

1. 学习主线失焦
   - 你会同时处理太多新变量
2. 项目骨架还没吃透
   - 反而会把 `v1` 已经验证过的主链冲散

所以更合理的推进方式不是：

- “继续在 `v1` 里悄悄加更多功能”

而是：

- 明确宣布 `v1` 到这里收束
- 然后带着清晰问题进入 `v2`

## `v2` 最值得优先做什么

如果进入 `v2`，
我更建议优先沿着下面这几条线继续：

### 1. 真实环境部署路径

把 `mini-cloud`
从本地开发实验，
推进到一套更真实的阿里云运行环境。

这里最先值得补的是：

- control-plane 部署方式
- agent 安装与升级
- 配置与密钥管理
- 真实域名和入口接入

### 2. 更正式的入口层

`v1`
已经证明“应用能被发布并对外暴露”，
但入口层还比较轻。

`v2`
可以继续把这些问题做完整：

- 路由模型
- TLS
- 多域名
- 默认入口与项目级入口

### 3. 更正式的节点与资源抽象

到了 `v2`，
才适合认真讨论：

- provider 抽象
- region / zone / failure domain
- 节点发现与节点池

### 4. 更强的运维与可靠性能力

这里包括：

- 更细的告警
- 更清晰的运维动作审计
- 更完整的失败恢复路径
- 更可靠的版本升级策略

## 到这里，应该怎样理解 `mini-cloud v1`

最适合的理解方式是：

- 它已经完成了“平台骨架搭建”
- 但还没有进入“平台能力扩张”

也就是说，
`v1` 的意义不在于：

- 功能数量很多

而在于：

- 关键对象已经稳定
- 主链已经能跑通
- 测试和文档已经能支撑后续继续演进

如果用一句话收束 `v1`，
我会这样描述：

- `mini-cloud v1`
  - 已经把“一个最小容器应用平台”从想法做成了可运行骨架
  - 下一步不是继续乱加功能
  - 而是带着清晰边界进入 `v2`
