# 00 Overview

这一章只做三件事：

1. 说明 `mini-cloud` 想解决什么问题
2. 说明 `v1` 先做什么、不做什么
3. 建立最小总体架构直觉

## 这条项目线想解决什么

我们现在已经有：

- 多条基础知识主线
- 多台分布在不同 provider / region 的机器
- 一定的远程实验能力

所以现在值得开始做的，
不是继续孤立地学更多零散主题，
而是把这些能力收束成一个真实系统。

`mini-cloud` 的第一版，
就是这个“收束动作”。

不过这里还有一个很重要的收敛动作：

- `mini-cloud`
  - 是长期目标
- `v1`
  - 不是一步到位做“多云平台”

`v1` 会先把底层后端固定成：

- 阿里云
- `ECS`

原因很简单：

- 我们当前真实学过、做过实验、已经有经验沉淀的云后端
  - 主要就是阿里云
- 现在最重要的是先把：
  - 控制面
  - agent
  - 调度
  - 发布
  - 观测
  - 这一整条主链跑通
- 而不是一开始就把问题扩大成：
  - “怎么统一抽象不同云厂商”

所以：

- `v1`
  - 先是：
  - `aliyun-only backend`
- `v2`
  - 再去做真正的多 provider 扩展

## v1 先做什么

`v1` 先只做：

- 纳管阿里云 `ECS` 节点
- 节点纳管
- 应用模型
- 发布模型
- 简单调度
- 运行时执行
- 基础入口
- 基础观测
- 基础用量统计

## v1 不做什么

`v1` 暂时不做：

- 多 provider 后端
- 虚拟机产品
- 完整云账单
- 完整认证系统
- 大而全的多租户隔离
- 很复杂的入口网关能力

## 最小架构直觉

`v1` 可以先粗略理解成四层：

1. 控制面
   - 负责资源模型、API、状态推进
2. 调度层
   - 负责把应用放到合适节点
3. 节点执行层
   - 负责真正拉镜像、起容器、回传状态
4. 配套层
   - 负责日志、指标、域名接入、成本统计

## 这一章结束后应该明确什么

看到这里，
你应该先明确这几点：

- `mini-cloud` 的第一版不是“迷你 AWS”
- 它更像一个：
  - 多地域容器应用平台
- `v1` 的底层后端先固定为：
  - 阿里云 `ECS`
- 我们要先把核心控制面跑通
- 缺的专题知识，后面再按项目需要补
