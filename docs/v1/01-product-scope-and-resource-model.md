# 01 Product Scope And Resource Model

这一章先不写代码，
先把第一版产品边界和资源模型说清楚。

## 为什么先做这件事

如果一开始不先定义：

- 第一版到底卖什么
- 第一版不卖什么
- 系统里有哪些核心对象

那么后面的：

- API
- 数据库
- 调度
- agent
- 发布状态机

都会很容易越写越散。

## v1 的产品边界

`v1` 提供的是：

- 多地域容器应用托管

而不是：

- 虚拟机产品
- 对象存储产品
- 托管数据库产品

也就是说，
第一版用户最核心的动作应该只有这些：

- 创建项目
- 创建应用
- 上传或指定镜像
- 选择：
  - region
  - 副本数
  - 资源规格
- 发起发布
- 查看状态、日志、基础指标

这里再强调一次：

- `v1`
  - 的底层节点来源先固定成：
  - 阿里云 `ECS`

也就是说，
这一版虽然项目名字叫：

- `mini-cloud`

但实现范围其实更接近：

- “面向阿里云 `ECS` 节点池的最小应用平台”

这样做不是退步，
而是为了把第一版先做稳。

## v1 的核心资源

建议先收成下面这些核心对象：

### `Project`

- 一个逻辑隔离边界
- 应用、域名、配额都挂在项目下面

### `Node`

- 一台被纳管的机器
- 在 `v1`
  - 它首先就是一台阿里云 `ECS`
- 需要带上：
  - `provider`
  - `region`
  - `capacity`
  - `status`

在 `v1` 里，
`provider`
字段虽然还会保留，
但它的值基本就是固定的：

- `aliyun`

这样做的意义是：

- 资源模型先保留未来扩展位
- 实现范围先保持收敛

### `App`

- 用户想长期运行的一个应用
- 它描述的是“我想运行什么”

### `Release`

- 一次可追踪的发布版本
- 通常会绑定：
  - 镜像
  - 环境变量
  - 版本号

### `Deployment`

- 某个 `Release`
  - 在某个目标范围里的实际投放结果
- 它更接近期望状态和实际状态之间的桥梁

## v1 的用户面长什么样

`v1` 的用户面，
我建议不要做成：

- 云厂商资源控制台

而是更接近：

- `Render`
- `Heroku`

这种“应用托管平台”的感觉。

也就是说：

- 用户不是来直接管理：
  - `ECS`
- 用户是来：
  - 部署一个容器应用

这会让第一版的产品语义更稳定。

## v1 的两类视角

建议从一开始就区分两类视角：

### 租户面

- 面向应用使用者
- 只暴露和“部署应用”直接相关的对象

### 平台面

- 面向平台管理员
- 负责看：
  - 节点
  - 容量
  - 心跳
  - 调度失败原因
  - 底层阿里云资源映射

这两个视角不要混在一起，
否则用户面会很快长成“半个平台后台、半个云控制台”的奇怪形态。

## 哪些对象暴露给普通用户

建议 `v1` 的普通用户只直接接触这些对象：

- `Project`
- `App`
- `Release`
- `Domain`
- `Usage`

这里面：

- `App`
  - 是用户长期关注的主对象
- `Release`
  - 负责表达一次发布
- `Domain`
  - 负责表达域名绑定
- `Usage`
  - 负责表达资源用量和成本预估

## 哪些对象先只放在平台面

这些对象我建议先只给平台管理员看：

- `Node`
- `Region`
- `Capacity`
- `Heartbeat`
- `Maintenance`
- 调度失败详情
- 阿里云 `ECS` 映射信息

这样做的原因是：

- 普通用户不需要知道底层是哪台 `ECS`
- 普通用户更关心：
  - 应用能不能跑
  - 当前版本是什么
  - 为什么发布失败
- 节点细节更适合先放到平台内部

## v1 先支持哪一种应用

`v1` 先只支持一种最小应用形态：

- 长跑型 `HTTP` 容器应用

也就是先只支持：

- 一个镜像
- 一个主监听端口
- 一组环境变量
- 一个健康检查
- 一个地域
- 若干副本

暂时先不支持：

- `Job`
- `Cron`
- `Worker`
- 多端口服务
- 挂卷
- 托管数据库绑定

这会让：

- 入口模型
- 健康检查
- 发布状态机

都简单很多。

## v1 的入口形态

我建议第一版按这个优先级推进：

1. `API`
2. `Web`
3. `CLI`

也就是说：

- `API`
  - 是真相源
- `Web`
  - 会在 `v1`
  - 就直接做
  - 但仍然保持“薄控制台”定位
- `CLI`
  - 可以后补
  - 不要求一开始就先做出来

这样更符合我们当前的目标：

- 先把平台模型和控制链路打稳
- 同时也尽早把用户视角真正可视化

## v1 为什么可以直接上 React

这里需要强调一下：

- 我们现在同意：
  - `v1`
  - 直接上 `React`

这不表示项目要变成：

- “前端优先”

更准确地说，
这里的取舍是：

- 需要网页
- 也愿意尽早把控制台搭起来
- 但控制台仍然服务于：
  - 平台资源模型
  - 平台状态查询
  - 平台操作入口

所以：

- 前端会用：
  - `React`
- 但产品边界仍然是：
  - 薄控制台
  - 不是重前端平台产品

## v1 前端的范围

如果按这个方向来做，
那么第一版前端建议先只覆盖这些页面：

- 项目列表
- 应用列表
- 应用详情
- 发布记录
- 节点列表
- 最近事件

也就是说：

- 先把最需要“可视化”的平台状态做出来
- 不一开始就冲到：
  - 很复杂的设计系统
  - 很复杂的交互模型
  - 很重的控制台壳子

## 普通用户最核心的动作

如果按这个产品边界来收，
那么 `v1` 的普通用户最核心的动作应该只有这些：

1. 创建项目
2. 创建应用
3. 填镜像、端口、环境变量、健康检查
4. 选择地域
5. 选择副本数和规格
6. 发起发布
7. 查看状态、日志、事件
8. 绑定域名
9. 回滚到旧版本
10. 调整副本数

## 这一章的结论

走到这里，
`v1` 的产品面应该已经比较明确了：

- 它不是阿里云资源控制台
- 它更像一个：
  - 面向阿里云 `ECS` 节点池的应用托管平台
- 普通用户看的是：
  - `Project`
  - `App`
  - `Release`
- `v1`
  - 会直接提供：
  - `React`
  - 控制台
- 平台管理员看的是：
  - `Node`
  - `Capacity`
  - `Heartbeat`
- 第一版先只支持：
  - 长跑型 `HTTP` 容器应用

## 这一章的输出

这一章之后，
后续实现至少要围绕这些问题继续展开：

- 资源之间怎么关联
- 哪些字段是期望状态
- 哪些字段是观察状态
- 哪些状态由控制面负责推进
- 哪些状态由 agent 上报

这些会直接决定：

- API 长什么样
- 表结构长什么样
- orchestrator 怎么写
