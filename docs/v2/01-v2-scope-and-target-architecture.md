# 01 V2 Scope And Target Architecture

这一章是 `v2` 的正式开篇。

它先不急着写实现，
而是先把三件事说清楚：

1. `v2` 到底要解决什么
2. `v2` 和 `v1` 相比，核心变化在哪
3. `v2` 的目标架构应该怎样分层

如果这三件事不先说清楚，
后面的：

- `bootstrap`
- 阿里云资源创建
- 平台安装
- `TLS`
- 审计
- 备份与恢复

就很容易越做越散。

## 先给 `v2` 下一个准确定义

`v2`
不是要把 `mini-cloud`
突然做成：

- 多云平台
- 高可用控制面
- Kubernetes 平台
- 云厂商控制台

`v2`
更准确的定位是：

- 把 `v1` 的最小平台骨架
  - 推进成一个完整的阿里云单 provider 项目
  - 它不仅能托管应用
  - 还要能先把平台自己安装到阿里云上

所以：

- `v1`
  - 解决的是：
  - “这条平台主链能不能成立”
- `v2`
  - 解决的是：
  - “这条主链能不能先完成自安装，再放进真实环境长期运转”

## 为什么 `v2` 还不急着做第二家 provider

这一步很容易被误判。

表面上看，
`mini-cloud`
这个名字很容易让人觉得下一步就应该做：

- AWS
- 腾讯云
- 裸机

但从工程顺序看，
现在最缺的其实不是：

- “再接一家后端”

而是：

- “先把第一家后端上的完整生命周期做出来”

这里说的完整生命周期，
至少包括：

- 平台自己的资源怎么创建
- control-plane 怎么安装
- worker 怎么纳管
- 域名和 `TLS` 怎么接
- 日志、告警和 runbook 怎么闭环
- 数据怎么备份和恢复

如果这些问题都还没收干净，
就直接扩到第二家 provider，
项目很容易出现一种假进展：

- 抽象越来越多
- 但真实可运维性并没有明显变强

所以 `v2`
仍然先保持：

- 阿里云单 provider
- 单 active control-plane

这是一个主动收敛，
不是能力不足。

## `v2` 必须先分成两层

这一点必须先说死，
否则后面很容易把“平台安装器”和“平台本体”混在一起。

### 1. `bootstrap layer`

这一层运行在：

- 你的本机
- 或一台带 `RAM` 权限的 seed `ECS`

它负责：

- 创建和更新平台自己的阿里云资源
- 输出一份稳定的 resource inventory
- 首次安装平台
- 平台重装、升级、销毁

这层不是长期运行的 control-plane，
它更像：

- 平台安装器

### 2. `platform layer`

这一层运行在：

- `bootstrap` 创建出来的 platform `ECS`
- 以及后续被平台纳管的 worker `ECS`

它负责：

- control-plane
- web
- gateway
- `Postgres`
- `agent`
- 应用托管
- 平台运维

所以从 `v2` 开始，
要形成一个很清晰的心智模型：

- `bootstrap` 先把平台自己的基础设施和平台本体装起来
- 平台启动后再去做应用托管

## 从现有代码看，`v1` 已经稳定了什么

在开始谈 `v2` 前，
先把当前代码里已经稳定下来的模块看清楚。

现在 `mini-cloud`
大致已经有这些结构：

- `cmd/control-plane`
  - control-plane 入口
- `cmd/agent`
  - 节点侧 `agent`
- `internal/httpapi`
  - API 路由和处理器
- `internal/store`
  - `Postgres` 读写和 migrations
- `internal/scheduler`
  - 最小放置逻辑
- `internal/deployment`
  - deployment 状态推进
- `internal/execution`
  - 节点执行工作项
- `internal/runtime`
  - 当前运行时封装
- `internal/ingress`
  - 基础入口相关逻辑
- `internal/observability`
  - 指标和平台观测
- `internal/usage`
  - 用量、配额、成本预估

数据库里也已经有了这些核心对象的基础表：

- `projects`
- `nodes`
- `apps`
- `releases`
- `deployments`
- `placement decisions`
- `deployment executions`
- `domains`
- `gateway request events`
- `project quotas`

也就是说，
`v2`
不是在一片空地上开始，
而是在一个已经具备：

- 控制面
- 数据模型
- 节点执行链
- 基础入口
- 基础观测

的系统上继续往前推。

## `v2` 里什么保持不变

先把不变的东西说死，
后面才不会越做越散。

### 1. 产品形态仍然是“应用托管平台”

`v2`
仍然不是：

- 卖虚拟机
- 卖对象存储
- 卖数据库

它依然更接近：

- `Render`
- `Heroku`

这种应用托管平台。

### 2. 用户关心的核心对象不变

用户面最核心的对象，
仍然是这些：

- `Project`
- `App`
- `Release`
- `Deployment`
- `Domain`
- `Usage`

也就是说，
`v2`
不会把用户面突然改成一个“云资源控制台”。

### 3. control-plane + agent 的大框架不变

`v2`
不会推翻 `v1`
已经成立的这条主链：

- control-plane 决定应该发生什么
- `agent` 让节点上真的发生
- `Postgres` 记录状态推进到了哪里

### 4. 底层运行面暂时仍然保持最小

`v2`
依然不急着把底座切成：

- `k3s`
- Kubernetes

因为当前最重要的还是：

- 把平台自安装和真实运维做好

而不是同时把运行时底座也换掉。

## 哪些资源属于 `v2` 要自动创建的平台自有资源

`v2`
要自动创建的，
首先是平台自己的基础设施，
而不是租户专属基础设施。

这一点要分清，
否则范围会立刻炸开。

平台自有资源至少包括：

- `VPC`
- `vSwitch`
- `SecurityGroup`
- `EIP`
- platform `ECS`
- first worker `ECS`

后面如果需要，
也可以继续把这些平台配套资源纳入 `bootstrap`：

- DNS 记录
- 证书相关辅助资源
- 平台自己的对象存储桶

但无论怎么扩，
它们都应该满足一个前提：

- 这些资源是平台自己为了“先把自己跑起来”而创建的

## 哪些问题明确留给 `v3`

`v2`
不去做下面这些事：

- 根据某个租户需求，
  - 自动创建独立 `ECS`
- 根据某个应用需求，
  - 自动创建独立 `VPC`
  - 或数据库
- 平台根据租户级隔离要求，
  - 自动铺独立网络和独立基础设施
- 第二家 provider 的真实接入

这些方向当然重要，
但它们属于：

- `v3`

也就是说，
`v2`
的目标是：

- 平台先把“自己”自动装起来

而不是：

- 平台已经开始“替用户”自动铺整套基础设施

## `v2` 到底新增什么

如果把 `v2`
和 `v1`
最本质的差别压缩成一句话，
那就是：

- `v1` 更像“平台骨架”
- `v2` 开始补“平台自安装能力”和“平台运行条件”

这些新增内容，
大致可以分成六层。

### 1. `bootstrap` 资源创建层

它回答的是：

- 平台自己的阿里云资源怎么创建
- 资源存在时怎样回读复用
- 资源冲突时怎样重试和幂等
- 平台销毁时怎样清理这些资源

这一层是 `v2`
和 `v1`
最大的新增差别。

### 2. 安装与首次启动层

它回答的是：

- 新创建的 platform `ECS` 怎样被初始化
- migration 怎么执行
- 配置文件和环境变量怎么组织
- 服务进程怎么被托管
- 第一轮健康检查怎么完成

这部分会把“开发机里 `go run` 能跑”
推进成：

- “阿里云里新机器拿到后可以自动完成安装和启动”

### 3. 节点运维层

它回答的是：

- `agent` 怎么安装
- `agent` 怎么升级
- 节点怎么重连
- 节点怎么进入维护模式
- 节点怎么恢复接流量

这部分的重点不是再发明一个新调度器，
而是让“已纳管节点”真的可维护。

### 4. 配置与凭据层

它回答的是：

- 应用配置怎么管理
- 敏感配置怎么管理
- 私有镜像仓库凭据怎么下发
- 节点执行时怎么安全使用这些信息

这一层是 `v1`
里很明显还缺的一块，
因为真实环境里如果没有这层，
很多应用根本无法安全上线。

### 5. 入口与访问控制层

它回答的是：

- 域名怎么正式接入
- `TLS` 怎么申请和续期
- 管理员怎么登录
- 项目级 API Token 怎么控制
- 关键操作怎么留下审计记录

这部分不是在追求“完整 IAM”，
而是在补最小但真实可用的访问边界。

### 6. 运维与恢复层

它回答的是：

- 哪些指标需要告警
- 平台出故障时先看什么
- 哪些动作必须写 runbook
- 数据怎么备份
- control-plane 损坏后怎么恢复

这部分决定的不是“功能多不多”，
而是：

- 这个平台出问题后你能不能把它救回来

   - 备份恢复

也就是说，
`v2`
不是简单“多几个 API”，
而是让平台外围条件逐渐完整。

## 哪些新增东西应该做成“资源对象”

这里要克制，
不要看到一个新需求就立刻加一张表、一个公开 API。

### 第一类：适合做成明确资源对象

这些东西更适合逐步做成正式对象：

- `Secret`
- `APIToken`
- `AuditEvent`
- `NodePool`
- `BootstrapInventory`

因为它们：

- 生命周期明确
- 很可能被查询
- 很可能被审计
- 很可能被 UI 展示

### 第二类：更像平台内部能力，不必急着变成用户资源

这些东西可以先作为平台内部能力存在：

- `TLS` 证书签发流程
- 备份任务执行器
- 恢复动作编排
- 告警投递实现

原因是：

- 这些能力确实重要
- 但不一定需要一开始就做成对用户完全开放的资源模型

这会让 `v2`
的资源模型扩张速度更可控。

## `v1 -> v2` 最值得记住的变化

| 维度 | `v1` | `v2` |
| --- | --- | --- |
| 平台定位 | 最小平台骨架 | 完整的阿里云单 provider 项目 |
| 后端范围 | 阿里云单 provider | 仍是阿里云单 provider |
| 云资源准备 | 主要靠手工或实验脚本 | `bootstrap` 自动创建平台自有资源 |
| 关注重点 | 主链是否成立 | 平台能否先自安装，再真实运维 |
| 节点视角 | 能注册、能执行 | 能安装、升级、维护、重连 |
| 入口 | 基础域名绑定 | 正式 gateway + `TLS` |
| 配置 | 主要还是演示级 | 区分普通配置与敏感信息 |
| 安全边界 | 基础版 | token、审计、最小访问控制 |
| 恢复能力 | 很轻 | 备份、恢复、runbook、告警 |
| 验证方式 | 本地测试 + smoke | 模拟完整 example + `bootstrap` 验收 + 真实阿里云验收 |

最关键的一点其实是：

- `v2`
  - 不是把 `v1` 推倒重来

而是：

- 把 `v1` 已经成立的主链
  - 放进一个完整的阿里云安装与运维闭环里继续打磨

## 这一章结束后，后面各章在干什么

如果把后面章节压缩理解，

- `05`
  - 让 platform / worker 拓扑和持续纳管主链真正成型
- `06`
  - 补上 secrets 和镜像凭据
- `07`
  - 把发布过程做得更安全
- `08`
  - 把 gateway 和 `TLS` 做正式
- `09` `10`
  - 补最小认证、token、审计和基础角色边界
- `11` `12`

所以从这一章开始，
`v2`
就不再只是“多做几个功能”，
而是在做一件更像真实平台工程的事情：

- 把一个能跑的系统
  - 变成一个能先把自己安装起来，
  - 再能长期维护和恢复的系统
