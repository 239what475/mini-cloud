# 17 v2 Final Review

到这一章，
`mini-cloud v2`
就不再继续往前铺新功能了。

这一章要做的事情很简单：

- 回头看
  `v2`
  到底做成了什么
- 明确
  `v2`
  故意没有做什么
- 给
  `v3`
  留出一个更清楚的起点

如果不做这一步，
前面的十几章虽然都成立，
但你很容易在脑子里把它们记成：

- 一堆散点能力

而不是：

- 一条完整版本线

## 先用一句话总结 v2

如果说：

- `v1`
  解决的是
  - “平台骨架能不能成立”

那么：

- `v2`
  解决的就是
  - “这个平台能不能先把自己装到阿里云上，再在真实环境里部署、升级、重装、恢复和销毁”

所以 `v2`
最核心的关键词不是：

- 多 provider
- 高可用 control-plane
- 很重的产品面

而是：

- 单 provider
- `bootstrap`
- 平台自安装
- 真实环境
- 模拟环境
- 运维入口

## v2 最终做成了什么

现在可以把 `v2`
真正做成的东西分成六块看。

### 1. bootstrap layer 已经成立

这一层负责的不是托管应用，
而是：

- 创建平台自己的阿里云资源
- 发现已有受管资源
- 做首次安装、重跑、升级、重装、销毁

到 `v2` 结束时，
这层已经能处理：

- `VPC`
- `vSwitch`
- `security group`
- 平台 `ECS`
- `EIP`
- 平台 RAM role

而且不是单纯的“只会创建”，
还包括：

- discover-first 的 `apply`
- `destroy`
- 幂等重跑

这很重要，
因为它让 `mini-cloud`
第一次具备了：

- 平台先把自己装起来

的能力。

### 2. platform layer 已经不只是骨架

到了 `v2`，
平台层已经不只是：

- “能注册节点”

而是有了一条完整的应用托管主链：

- worker 纳管
- release 提交
- deployment 状态推进
- runtime 启动容器
- 健康检查
- gateway 转发
- rollback
- 基础审计
- 配额 / 用量 / 基础运维视图

也就是说，
`v2`
结束时的 `mini-cloud`
已经可以被理解成：

- 一个最小可用的容器应用平台控制面

而不是：

- 只有若干独立 API 的 demo

### 3. 本地完整模拟环境已经成立

这一点是 `v2`
特别关键的成果之一。

现在本地已经不只是：

- 单元测试
- store 测试
- 一条最小 smoke

而是多了一套完整组合环境：

- `./scripts/simulated-env.sh`

它能把下面这些东西统一收起来：

- 本地 `Postgres`
- control-plane
- 两个 managed worker
- demo app
- 发布 / 回滚 / 节点掉线 / 备份恢复场景

这意味着：

- `v2`
  后续回归不必每次都直接上阿里云

先在本地把组合问题拦掉，
再去做真实云验收，
这就是这一版很重要的工程价值。

### 4. 备份恢复和灾难演练已经有了最小闭环

`v2`
没有把“灾难恢复”停在概念层。

现在已经有：

- `backup-platform.sh`
- `restore-platform.sh`
- `disaster-drill.sh`

这说明平台已经开始具备：

- 把数据库状态打出来
- 把数据库外配置一起收进 bundle
- 模拟损坏后恢复回来

的最小运维能力。

这类能力表面上不像发布那样显眼，
但从平台工程和 `SRE`
学习角度看，
它非常关键。

### 5. 真实阿里云验收入口已经成立

到 `v2`
结束时，
真实云入口已经不是一句“理论上可行”，
而是有了明确脚本：

- `./scripts/real-aliyun-lab.sh`

而且它已经覆盖：

- `install`
- `status`
- `demo`
- `upgrade`
- `reinstall`
- `cleanup`
- `destroy`

更重要的是，
这些不只是脚本设计，
而是真的在阿里云里跑过。

这件事把 `v2`
和单纯“本地项目练习”拉开了。

### 6. 文档和代码已经形成章节式检查点

从项目结构上看，
`mini-cloud`
这一条线现在已经比较稳定地形成了：

- 代码
- 教程文档
- 每章一个 commit 检查点

这让它不只是一个“代码仓库”，
也不只是一个“教程仓库”，
而是两者真的绑在一起的学习项目。

## v2 最重要的工程收获是什么

如果只挑最值得记住的几件事，
我会把 `v2`
的收获压缩成下面四条。

### 1. 平台工程不只是在写 control-plane

做 `v2`
以后会很清楚地看到：

- 真正把平台做出来
  并不只是在写 API 和状态机

你还得处理：

- 安装
- 远端运行环境
- 镜像拉取
- `systemd`
- 数据库
- 备份恢复
- 云资源生命周期

这也是为什么：

- `bootstrap layer`
- `platform layer`

在 `v2`
里必须明确分开。

### 2. 真实环境会暴露本地看不到的问题

这条在 `v2/15`
已经体现得很明显。

例如：

- 本地看起来没问题的 Docker 超时
- 到真实阿里云里第一次冷拉镜像就不够了

这类问题在本地模拟里未必出现，
但它们又是真实运维里很常见的毛刺。

所以：

- 本地完整模拟环境
  很重要
- 真实云验收
  仍然不可替代

### 3. 文档整理本身也是 hardening

很多人会把“文档整理”理解成：

- 临近结束时补点说明

但 `v2/16`
已经证明：

- 当脚本入口足够多时
- 不把边界整理清楚
  本身就是一种工程风险

也就是说：

- 文档不是收尾装饰
- 它本身就是运维入口的一部分

### 4. 小而完整，比大而空更有价值

`v2`
没有去追求：

- 第二家 provider
- 多副本 control-plane
- 真正的多租户 IAM
- 很重的云产品面

但它换来的好处是：

- 阿里云单 provider 这条线真的做完整了

这比“名义上支持很多方向，
但每条都只做到半截”
更有学习价值。

## v2 明确没有做什么

这一章也必须把“没做什么”说清楚。

因为不把边界说清楚，
后面版本就很容易失焦。

现在明确还不属于 `v2`
的主要有这些。

### 1. 没有真正接第二家 provider

虽然项目定位一直是：

- 面向多 provider / 多 region 的平台

但 `v2`
实际上只把：

- 阿里云单 provider

做完整了。

这是有意取舍，
不是遗漏。

### 2. 没有做高可用 control-plane

当前还是：

- 单 active control-plane

这意味着还没有处理：

- control-plane 自身的多副本高可用
- 控制面数据库的正式 HA 方案
- 正式的 leader 选举

### 3. 没有做真正的 provider abstraction

现在代码里虽然已经开始有：

- provider
- region

这些概念，
但它们还不足以说明：

- 你已经可以平滑接 AWS / 腾讯云 / 裸机

所以：

- 真正的 provider abstraction
  仍然属于后续版本主题

### 4. 没有做按租户需求动态申请独立云资源

这点在前面就已经明确留给：

- `v3`

当前平台管理的是：

- 平台自己的一套基础资源

还不是：

- 用户创建一个 app
  平台就自动给它单独申请一套云网络 / 云主机 / 云盘

### 5. 没有做很重的用户面和产品面

当前虽然已经有 `React`
前端和控制台方向，
但 `v2`
的重心始终不在：

- 大量产品页面
- 很复杂的前端交互
- 完整 IAM / 账单 / 支付

这些方向后面当然可能做，
但不应该反过来干扰：

- 平台核心
- 安装
- 运行
- 运维

这条主线。

## 那 v3 最合理的起点是什么

如果 `v2`
已经把：

- 单 provider
- 平台自安装
- 本地完整模拟
- 真实云验收

做完整，
那么 `v3`
最值得做的就不该是“再补几个零散 feature”，
而应该进入更高一层的问题。

我认为最合理的起点是三条。

### 1. 按租户或应用需求创建独立云资源

这是从：

- “平台管理自己的一套基础设施”

走向：

- “平台开始根据 workload 需求去申请资源”

的关键一步。

这是 `mini-cloud`
更像“云平台”而不只是“托管平台”的分水岭。

### 2. provider abstraction 与第二家 provider

如果一直停留在：

- 阿里云单 provider

那 `mini-cloud`
的很多长期目标都只是口头上的。

所以 `v3`
里比较值得认真做的一件事是：

- 真正抽出 provider 接口
- 再接入第二家 provider

哪怕第二家先接得很浅，
这一步本身也会强迫架构边界更清楚。

### 3. 更正式的控制面可靠性

等平台真的开始跨 provider / 跨 region，
就不能一直假定：

- control-plane 还是单点

所以：

- 控制面 HA
- 状态持久化策略
- 变更和恢复策略

会成为更自然的下一阶段主题。

## 现在回看 v2，最值得保留的是什么

如果以后还继续扩这个项目，
我最希望保留的不是某一个具体实现细节，
而是这几条方法。

### 1. 每章一个明确检查点

这让版本演进非常清楚。

### 2. 先做最小完整闭环，再扩

这是 `v2`
没有失控的重要原因。

### 3. 本地完整模拟环境和真实云验收并存

只做本地不够，
只做真实云也太重。

两条线并存，
是这版最合理的平衡。

### 4. 把真实环境里的毛刺记回文档

这会让教程越来越像真正的工程记录，
而不是只保留“理论上应该成功”的部分。

## v2 的最终结论

到这里，
可以比较稳地说：

- `mini-cloud v2`
  已经完成了它这一版最重要的目标

它现在已经不是：

- 一个只有本地 demo 的平台骨架

而是：

- 一个能在阿里云里把自己装起来
- 能托管最小容器应用
- 能在本地做完整组合回归
- 能在真实云里做升级、重装、销毁验收

的单 provider 平台项目。

这并不意味着：

- 它已经接近“真正的云厂商”

但它已经足够说明：

- 这条路线成立
- 下一版可以站在一个真实可运行的基础上继续往前走

这就是 `v2`
最核心的价值。
