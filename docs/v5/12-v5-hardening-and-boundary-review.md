# 12 v5 Hardening And Boundary Review

这一章不再继续补新功能。

到这里为止，
`v5`
真正要做的事情只剩三件：

- 回头看
  `v5`
  到底已经做成了什么
- 把
  `v5`
  故意没有做的边界写死
- 把真正还缺的硬化项，
  留给
  `v6`

如果不做这一步，
前面的章节很容易在脑子里变成：

- `gRPC`
  一段
- `Caddy`
  一段
- 身份和授权一段
- front door
  一段
- 双云
  `E2E`
  一段

而不是：

- 一个已经收成形状的多云 `CaaS`
  版本

## 上一章检查点

- `v5/11`
  - `d2a2976c67863e7f5c280176311aba191a7ee4ab`

## 先用一句话总结 v5

如果说：

- `v4`
  解决的是：
  - 多套独立 `cloud-plane`
    能不能被统一纳管
  - 三层边界能不能收清楚
  - 全局观察和运维面能不能成立

那么：

- `v5`
  解决的就是：
  - 能不能把这套底座收成一个只支持长期在线服务的多云 `CaaS`
  - 用户能不能围绕：
    - 服务定义
    - 配置与密文配置
    - 服务暴露
    - 发布
    - 回滚
    - 扩容
    - 观测
    来真正使用平台

所以
`v5`
最核心的关键词不是：

- 新 workload 类型
- 新 provider
- 更重的全局流量系统

而是：

- `service-only`
- `service cell`
- `cloud-plane + gateway + agent`
  的执行闭环
- 全局 `project / service / front door route`
  模型
- 一条真实可执行的双云 operator
  主链

## v5 最终做成了什么

现在可以把
`v5`
真正做成的东西分成六块看。

### 1. `service-only` 的产品边界已经正式成立

`v5`
最重要的收口，
不是“又多了几个对象”，
而是把平台边界重新压回：

- 只支持容器
- 只支持长期在线服务
- 只保留：
  - `service`
    这一个核心工作负载对象

这意味着：

- `job / cron / oneoff`
  没有再混进主线
- `v5`
  可以被更准确地理解成：
  - 一个多云长期在线服务平台

### 2. 单云 `service cell` 的执行闭环已经成立

到
`v5`
结束时，
一个单云执行面已经不再只是：

- 起一个 `cloud-plane`

而是已经有了完整闭环：

- 固定入口机
- `cloud-plane`
- `Caddy`
  网关
- 本机受限小 `node`
- 按需申请和回收的
  `runtime node`
- 节点侧 `agent`

也就是说，
单个 `service cell`
现在已经能自己完成：

- 节点接入
- 服务部署
- 配置下发
- 发布推进
- 网关收敛
- 扩缩容
- 运行时节点回收

### 3. fleet `control-plane` 的全局模型已经成立

`v5`
不是只把单云执行面做厚了。

这一版同样把全局管理面收成了真正可用的一组对象：

- `project`
- `service`
- `project resources`
  - `config set`
  - `secret set`
  - `registry credential`
- placement
- front door route
- incident / operation history

所以到了这里，
用户不再只是直接去操作某个云里的：

- `cloud-plane`

而是可以通过 fleet
看到和管理：

- 全局项目
- 全局服务
- 全局入口
- 全局放置结果

### 4. 配置、密文配置和项目资源绑定已经成立

这一块虽然没有发布和网关那么显眼，
但它其实是：

- 平台到底是不是“可用”

的关键分水岭。

到
`v5`
结束时，
平台已经不是只能收一个镜像和端口，
而是已经能收和下发：

- 配置
- 密文配置
- 镜像访问凭据

并把这些输入，
围绕：

- `project`
- `service`
- 目标 `plane`

形成明确的 ensure 和 binding
关系。

### 5. 发布、回滚、扩容和维护过滤已经有了 operator 主链

`v5`
最后成立的，
不是“可以发一次服务”这么简单。

更重要的是，
围绕 operator 日常操作，
现在已经有了一条连续主链：

- 创建项目
- 创建服务
- 绑定配置和密文配置
- 创建外部 route
- 发布新 revision
- 根据放置结果分发到目标 `plane`
- 扩容
- 回滚
- 过滤维护中的 `plane / node`
- 在 `plane`
  离线后做状态更新和放置收敛

这让
`v5`
第一次具备了：

- “像平台运维一样操作”

的感觉，
而不是：

- 只会调用零散接口

### 6. 验证入口已经分层，不再全靠单次手工实验

到了这一章，
`v5`
的验证强度已经分成了几层，
而不是把所有东西都混成一句：

- “理论上可行”

当前至少已经有：

- 真实单云 `E2E`
  - 阿里云
  - 腾讯云
- 真实双云 operator
  级 `E2E`
- 本地身份授权 `E2E`
- 本地应用观测 `E2E`
- 控制面 / 执行面
  集成测试

这件事很重要，
因为它说明：

- `v5`
  不是只做了一条很重、很贵、很难重复的真实实验
- 它已经开始形成：
  - 不同强度
  - 不同成本
  - 不同关注点
    的验证分层

这里也要说得更准确一点：

- 真实双云 `E2E`
  覆盖的是 operator
  主链
- 身份授权更偏：
  - 本地 `E2E`
- 一些更细的资源翻译和边界条件，
  仍然主要依赖：
  - 集成测试

所以
`v5`
已经不是“没有验证”，
但也不能把所有能力都写成同一强度的已验收结果。

## v5 当前明确不做什么

这一节一定要写死，
否则
`v5`
很容易被误读成一个范围比实际大得多的版本。

### 1. fleet `control-plane` 还没有统一成 `gRPC + grpc-gateway`

这一点要说准。

到
`v5`
结束时：

- `cloud-plane`
  的 northbound 管理接口，
  已经收成：
  - `gRPC`
  - `grpc-gateway`
- 但 fleet `control-plane`
  的 northbound 接口，
  当前仍然是：
  - `HTTP JSON`

所以
`v5`
不能被描述成：

- “整个平台 northbound
  都已经统一到
  `gRPC + grpc-gateway`”

更准确的说法应该是：

- `cloud-plane`
  先完成了这一步
- fleet `control-plane`
  还没有

### 2. front door 还不是厂商级 `CDN / DNS / TLS` 正式接入

`v5`
现在已经有：

- front door
  对象模型
- route reconcile
- 可执行代理

但它还不是：

- 阿里云 `CDN`
  正式接入
- 腾讯云 `CDN`
  正式接入
- 公网 `DNS`
  自动编排
- 正式公网 `TLS`
  厂商链路验收

也就是说，
这一版真正完成的是：

- front door
  语义
- route
  管理
- 执行链路模拟与验收

不是：

- 厂商边缘产品的正式集成

### 3. fleet `control-plane` 还不是正式高可用管理面

`v5/11`
做成的是：

- 本地单实例 fleet `control-plane`
- 双云真实 `cloud-plane`
- 双云真实 `service cell`

这已经足够验证：

- 多云 `CaaS`
  主链

但它还不是：

- 云上正式部署的 fleet 管理面
- 多副本 fleet
- 多活 fleet
- 对等同步的双 `control-plane`

### 4. 身份模型还没有在 fleet 和 `cloud-plane` 两层完全统一

这一版里，
`cloud-plane`
的身份和授权已经比较完整，
包括：

- 人类用户
- `platform service account`
- `project token`
- 前置认证链

但 fleet 这一层，
当前仍然更偏：

- `admin token`
- `project token`

的模型。

所以
`v5`
也不能被写成：

- “整个平台已经有一套完全统一的人类身份与授权体系”

更准确的说法是：

- `cloud-plane`
  这条线已经明显更成熟
- fleet
  这一层还没有完全跟上

### 5. `project` 仍然是单 owner 的简化模型

`v5`
为了把主线收紧，
故意没有走向：

- 多人共享项目
- 复杂成员关系
- 多档项目内角色

当前更准确的理解是：

- 一个 `project`
  固定只属于一个 owner
- 一个 `project`
  下面可以有多个 `service`

这让
`v5`
可以把重点继续放在：

- 多云 `CaaS`
  主链

而不是：

- 很重的多租户协作系统

### 6. 资源回收仍然更依赖“两段式”流程

当前真实云回收路径，
更准确地说是：

- 先走平台 `teardown`
- 再走 `terraform destroy`

这意味着：

- `destroy`
  不是“天然就会干净回收所有运行时资源”
- 当平台已经失联时，
  回收路径会明显变弱

也就是说，
这一版的资源回收已经：

- 可用
- 可验证

但还没有做到：

- 完全靠更强的内建控制器和恢复逻辑收敛

### 7. 更大的产品面故意没有再开

到这里为止，
`v5`
明确没有继续去做：

- `job / cron / oneoff`
- `service mesh`
- 第三家 provider
- 有状态服务主线
- 支付 / 余额 / 账单
- 对象存储 / 数据库产品线

这不是说这些东西没有价值，
而是：

- 它们不该继续压过
  `v5`
  的长期在线服务主线

## v5 最值得诚实写出的残留风险

这一节不是为了否定
`v5`，
而是为了把下一版真正该做的事情说准。

### 1. 文档叙事和实现强度不能混写

如果不把边界写清楚，
`v5`
很容易被误读成：

- 整个平台都已经
  `gRPC`
  化
- 真实 `CDN`
  已接入
- fleet
  已经是正式生产管理面

而这些都不是当前仓库现状。

所以
`v5/12`
最重要的价值之一，
就是把这些表述压回准确版本。

### 2. 身份、信任和安全边界还没有收成一套完整模型

当前问题不在于：

- 平台完全没有身份和授权

而在于：

- fleet
  和 `cloud-plane`
  这两层的成熟度并不一致
- token / secret / bootstrap
  的治理强度也不一致

这已经不是：

- 再补几个权限判断

就能解决的问题，
而是下一版应该系统处理的硬化项。

### 3. 清理、恢复和日常运维还更像 operator workflow

现在已经有：

- `teardown`
- `destroy`
- 备份
- 恢复
- 演练

但这些能力，
整体上仍然更像：

- 一套可信的运维流程

而不是：

- 一组完全产品化的后台控制器

这也解释了为什么：

- `v6`
  不该再开新产品面
- 而应该把现有平台做得更可运营

### 4. 可观测性、安全和运行时治理已经有骨架，但还没到生产化

这一版已经有：

- 应用侧观测闭环
- 告警规则
- 基础身份与授权
- 节点扩缩与回收

但如果把目标提高到：

- 更像真实长期运行的平台

那当前还缺的仍然很多：

- 更强的 controller / reconcile
  收敛
- 更完整的内部信任链
- 更严格的 runtime safety
- 更正式的 operator `SLO`
- 更自然的 `day-2`
  维护和替换流程

## 为什么 `v6` 不该继续扩产品面

到了这里，
下一版最自然的问题已经不是：

- 还要不要再加一个新对象
- 还要不要再接第三家云

而是：

- 这套平台能不能真正更稳定地收敛
- 能不能更安全地运行
- 能不能更像一个长期可运维的多云 `CaaS`

所以
`v6`
更合理的方向不是：

- 继续摊大产品面

而是：

- 生产化硬化

也就是把重点放到：

- 控制器化收敛
- 服务拓扑和更安全的发布
- front door
  健康路由与故障切换
- 控制链路安全、
  token / secret / 证书轮转
- `day-2`
  运维
- operator
  级可观测性

## 这一版最后怎么定义

如果要给
`mini-cloud v5`
下一个最准确的定义，
我会写成：

- 一个已经有真实双云 operator
  主链、
  但仍然保持清晰边界的多云长期在线服务型 `CaaS`

它不是：

- 一个完整公有云
- 一个完整多租户平台
- 一个正式多活管理面

但它已经不再只是：

- 若干散点实验

而是真正收成了一条清楚的版本线。
